# 测试

测试有两个作用:**驱动实现**(TDD)和**作为验证信号**(改完跑一遍确认没坏)。写测试的目标是"抓住真实回归",不是"凑覆盖率数字"。

## TDD:红 → 绿 → 重构

1. **红**:先写一个表达期望行为的测试,运行它、**确认它失败**(证明测试确实在测东西,而不是恒真)。
2. **绿**:写最小实现让它通过。
3. **重构**:测试保持绿的前提下清理结构。
> 修 bug 时同样适用:先写一个能复现 bug 的失败测试(红),修好让它变绿——这个测试从此守住这个 bug 不复发。

## 什么是好测试

- **测行为,不测实现细节**:断言"给定输入得到什么输出 / 什么可观察效果",而不是内部私有调用顺序;否则一重构测试就碎。
- **覆盖边界与错误路径**:空 / null / 0 / 超大 / 非法输入、异常分支、并发——bug 大多藏在这里,别只测 happy path。
- **断言有意义**:断言真正关心的结果;避免只断言"没抛异常"这种空测试。
- **独立、确定**:测试之间不相互依赖,不依赖时钟 / 随机 / 网络 / 执行顺序(该 mock 的外部依赖才 mock)。
- **克制 mock**:只 mock 真正的外部边界(网络 / DB / 时钟)。**别把被测逻辑也 mock 掉**——那样测的是 mock 不是代码。

## 跑测试 = 验证信号

- 每次改完跑相关测试;**以非零退出码为统一失败信号**,红了就回头修。
- 既要让目标测试**由红转绿**(修好该修的),又要保证**原本通过的测试仍通过**(没引入回归)。
- 交付时出示测试输出作为证据。

## 各语言速查(用项目已有的框架 / 脚本,别自造)

| 生态 | 常见跑法 |
|---|---|
| Node/TS | `npm test` / `npx vitest` / `npx jest`(先看 package.json 的 scripts) |
| Python | `pytest` / `python -m pytest -k <name>`(先看有没有 venv / 依赖) |
| Go | `go test ./...` |
| 其它 | 先看仓库的测试配置 / CI 脚本,沿用既有约定与目录结构 |

> 先探明项目**已有的测试框架、目录约定、运行命令**(读 package.json / pyproject / Makefile / CI 配置),沿用它;不要凭空引入新框架。

## 纪律

- **绝不为了让测试变绿而改测试期望 / 删断言 / suppress 失败**去迁就有问题的实现——那是 reward hacking,是假通过。测试红了,改实现,不改测试(除非测试本身写错了,并说明理由)。
- 测试要能**真正失败**:新写的测试先确认它在未实现时会红,避免写出恒真的空测试。
