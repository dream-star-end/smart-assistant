# 调试

调试的核心不是"改到看起来好了",而是**理解为什么错**再修。跳过复现直接猜改,往往按下葫芦浮起瓢。

## 流程:复现 → 定位根因 → 修 → 验证

### 1. 复现(先于一切)
- 拿到一个**确定能触发问题的最小用例**:一条命令、一个失败测试、一段输入。没有稳定复现就先想办法造一个(缩小输入、写个最小脚本 / 失败测试)。
- 记录**预期 vs 实际**,以及确切的报错信息 / 堆栈 / 退出码。

### 2. 定位根因(不停在症状)
- **读全报错**:完整堆栈往往直接指到出错文件行;`Read` 打开对应位置。
- **加可观测**:必要处插临时日志 / 打印中间值,或用 `Bash` 复跑观察;看清数据在哪一步变得不对。
- **二分缩小**:
  - 代码维度:注释 / 短路一半逻辑,看问题在哪半边。
  - 历史维度:`git log` / `git bisect` 找出是哪次改动引入的("以前好好的"类问题尤其有效)。
  - 数据维度:换输入,定位是哪类输入触发。
- **问到"为什么"**:定位到出错行后,继续追为什么会走到这——是上游传了脏数据?契约不一致?边界没处理?**找到最上游的那个因**,而不是最后崩的那个果。

### 3. 修根因
- 针对**根因**改,而不是把症状捂住。
- **禁止**:`try/except: pass` 吞掉异常、注释掉失败的断言、改测试期望迁就错误实现、`|| true` 掩盖非零退出——这些是假修复。
- 若同一根因会引发一类问题,一并根治;别只堵眼前这一个。
- 确因资源 / 时机只能临时绕过,显式标注"临时方案 + 根因 + 待偿还"。

### 4. 验证
- **用第 1 步的复现用例重跑**,确认问题消失。
- 跑相关测试 / 构建,确认没引入回归(原来通过的仍通过)。
- 出示证据:复现用例现在的输出 + 测试结果。

## 常用手段速查

| 场景 | 手段 |
|---|---|
| 定位报错源 | 读完整堆栈 → `Read` 对应 `file:line` |
| "哪次改动引入的" | `git log -- <file>` / `git bisect` / `git blame` |
| 运行期观察 | 插临时日志 / 打印中间态 → `Bash` 复跑(收尾记得删) |
| 缩小范围 | 二分注释代码 / 缩小输入 / 写最小复现脚本 |
| 环境 / 依赖问题 | 核对版本、依赖、路径、环境变量;`sudo apt` 补缺失工具链 |

> 收尾清掉调试用的临时日志 / 打印,别把调试残留留进交付代码。
