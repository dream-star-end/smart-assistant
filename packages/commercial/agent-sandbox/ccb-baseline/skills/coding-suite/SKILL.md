# 编程工作流总纲

目标是交付请求范围内、经实际验证的代码，不是交付一段看起来能跑的实现。
仓库强制门禁、权限与发布规则优先；本指南不授予安装、生产变更或扩大范围的权限。

## 按任务选路

- 实现功能：定位相关文件、调用方与既有模式后，选择最小合理改动。
- 修 bug：需要复现与根因定位方法时读 `debugging`。
- 写测试：需要设计测试或红绿对照方法时读 `testing`。
- 代码评审：用户要求 review 或复杂变更需要系统检查时读 `code-review`。
- 重构：先建立行为保护，再改结构并验证行为不变。

已能直接完成的局部修改，不为走流程叠加加载上述技能；既定独立审计不得省略。

## 完成边界

1. 改前读取相关代码；复杂任务先明确改动范围和验证方式，小改不必另写长计划。
2. 只改与请求有关的内容，沿用既有风格；不要全文件 reformat 或顺手重构。
3. 按影响面运行测试、构建、lint、typecheck 或实际程序，保留命令、输出和退出码。仓库要求的门禁仍须全部满足，不能以“局部修改”为由跳过。
4. 对本次改动引入的失败，在授权范围内定位、修复并重跑受影响验证，不在第一版实现后提前交差。无关基线失败须取证并报告，不擅自扩大范围；若它阻断仓库强制门禁，不得宣称通过或合入。
5. 交付前对照 diff 自审正确性、安全、回归与调试残留；小改做简短自审即可，不强制加载整套评审技能。
6. 缺关键输入、新增授权需求或真实阻塞时明确停点。区分“已实现”“已验证”“已发布”，未验证不能声称完成。

## 工具与安全

- 以当前工具列表为准，优先原生 Read/Grep/Glob 与精确编辑；未提供时使用可用的本地文件工具，不把本容器文件当宿主文件隔空读取。
- 不预检并自动安装整套依赖；遇到真实缺失先确认，优先使用现有替代工具，安装或系统变更遵循当前授权流程。
- 外部 API 先查官方文档或实际源码，不臆造签名、包名或命令结果。
- 修根因，不 suppress 报错、不改测试让它假过、不抄输出；临时止血须说明代价和后续条件。
- 破坏性操作、装包、出网前说明意图与影响，遵守权限边界；不硬编凭证，不装/用 AGPL/GPL 传染性许可库。
- 远程 push / PR 使用环境正式提供的认证路径，不假设 `gh` 或任何凭据已存在。
