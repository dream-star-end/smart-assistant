# 代码评审

对着**改动本身**评审,不是泛读整个仓库。以"陌生资深工程师第一次看这段 diff"的视角复查——这正是交付前自审最容易被跳过、又最能拦住回归的一环。

## 流程

1. **看全改动**:`git diff`(未提交)/ `git diff <base>..<head>`(分支)/ `git show <sha>`(某次提交)。先通读,建立"这次到底改了什么、为什么"的整体认知。
2. **对照意图**:改动是否真正解决了目标需求 / bug?有没有偏离范围(scope creep)或遗漏?
3. **分域逐查**(见下表),定位到 `file:line`。
4. **分级 + 给修法**:每条发现标级别,给出**可执行**的具体改法或复现路径,不只说"这里不好"。
5. **结论**:量化小结(如"改动 6 文件 / 2 个 critical / 5 条建议"),给"可合并 / 需修改后合并 / 阻断"的明确判断。

## 分域清单

**正确性**
- 边界与空值:空数组 / null / 0 / 超长输入 / 并发;off-by-one。
- 错误处理:异常有没有被吞?失败路径有没有回滚 / 释放资源?
- 逻辑:条件分支是否覆盖全?有没有引入回归(改动是否破坏了原有通过的行为)?
- 契约:改了函数签名 / 返回值 / 数据结构,所有调用方是否同步?

**安全**
- 注入:SQL / shell / 路径穿越 / 反序列化;用户输入是否校验与转义。
- 鉴权:新端点 / 操作是否有正确的 authz;有没有越权面。
- 机密:有没有硬编码 token / key / 密码;日志会不会打印敏感数据。
- 依赖:新引入的包是否可信、许可是否合规(禁 AGPL/GPL 传染)。

**性能**
- 有没有 N+1 查询、循环内 IO、无必要的全量加载、重复计算。
- 热点路径的复杂度;大数据量下是否会退化。(先定位真实瓶颈,别过早优化。)

**可维护性**
- 命名 / 结构是否与仓内既有风格一致;有没有引入第二套并行机制。
- 有没有调试残留(`console.log` / 注释掉的代码 / TODO)、死代码。
- 复杂逻辑有没有必要的注释说明"为什么";改动是否需要配套测试 / 文档。

## 分级

- **critical**:正确性 / 安全缺陷,会导致错误结果、数据损坏、安全漏洞或崩溃 → **必须改**。
- **warning**:潜在问题、回归风险、明显性能隐患 → 强烈建议改。
- **suggestion**:可读性 / 风格 / 小优化 → 可选。

## 纪律

- **只标真问题**:被要求"找 gap"时容易为了显得尽责而报一堆无关紧要的点,导致过度工程。**只标影响正确性 / 安全 / 需求的问题**,其余归 suggestion 并说明可选。
- 定位到 `file:line` + 给可执行修法,别停在抽象评价。
- 自审时对自己的改动同样严格:reward hacking(改测试让它过 / suppress 报错)在评审阶段就应被自己拦下。
