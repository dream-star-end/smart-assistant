# V5 个人版 Auto-Dream 现状与改进清单（OCV5-392，2026-10-13）

范围：个人版 `feat/v5-selfhost`（基线 fe489dedf，线上 rel-c82400b34）。商业版不动。
数据来源：代码阅读 + 个人版只读查询（`g392-ro-state.log`、`g392-ro-ready.log`、`g392-ro-price.log`）+ 用户卷上的状态文件。没有读任何记忆正文。

## 1. 现状

Auto-Dream 有两种模式，共用一个后台调度器（`packages/gateway/src/autoDream.ts`、`autoDreamOptimizer.ts`）：

| 模式 | 做什么 | 节奏 | 现状 |
|---|---|---|---|
| `legacy_memory_v1`（记忆整理） | 读近期会话摘录 + 现有记忆，用一次隔离（无工具）模型调用提出新记忆，只新增（ADD-only），自动写入 | ≥24h 且 ≥5 个新会话 | 后端完整可用；**网页上没有开关**（2026-07-23 被 v2 开关取代） |
| `optimizer_v2`（全面优化） | 审计会话/技能/设置，给出需用户确认的建议 + 平台发现 | ≥7 天 且 ≥5 个新会话 | 2026-10-09 OCV5-360 下线（从未产出过建议） |

线上事实（个人版，2026-10-13）：

- 所有用户卷（u3/u22/u247/u516/u765）都**没有** `auto-dream-state.json` 和 `auto-dream-optimizer-state.json`：Auto-Dream 在个人版**从未运行过一次**。
- 唯一 Max 用户 uid 3：`auto_optimizer_enabled=true`（下线前遗留）、`auto_dream_enabled=false`。打开 v2 时后端会把 v1 强制关掉（互斥）。
- v2 还要求遥测就绪：uid 3 有 7 个阻塞项（trace 覆盖 72%，门槛 95%；显式评分 1 条，门槛 3 条），所以策略接口返回 `{enabled:false}`。
- 结论：用户以为开着的功能，实际上什么也没做，界面也看不出来。

## 2. 触发条件（v1）

1. 一轮对话成功结束（签名、非报错、恰好一个 final、正文非空），渠道为 webchat、wechat 或 telegram。
2. 先在 SQLite 记一条“成功会话”标记，然后后台 `void maybeSchedule()`，不阻塞这一轮。
3. 同一会话 10 分钟内只扫描一次。
4. 自上次成功以来的不同会话数 ≥ 5，距上次尝试 ≥ 24 小时。
5. 策略（master 下发，失败一律视为关闭）：用户开了 `auto_dream_enabled`、Max 及以上有效订阅、`deepseek-v4-flash` 在目录中为 active+public+ccb。真正计费前还会强制刷新一次策略。
6. 文件锁 + attemptId 保证单实例；运行超过 2 小时算中断，报告为失败。

## 3. 成本

- 模型 DeepSeek V4.1 Flash：输入 112、输出 337、缓存读 3（积分/百万 token）。隔离的 CCB 会话，effort medium，按用户计费（workload `auto-dream`）。
- 单次输入上限：记忆快照 30k 字符 + 会话摘录 30k 字符 + 指令约 1.5k，约 ≤45k token，输出通常 <3k token。**单次 ≤ 约 6 积分**，最多每天一次，**月上限约 180 积分**。参照：uid 3 近 30 天 DeepSeek V4 Flash 正常对话 1367 次、2644 积分。
- 没有代码层的 token 上限，只靠提示词大小来限制（v2 没有这种限制，已下线）。

## 4. 质量问题（v1 代码层）

| # | 问题 | 位置 | 影响 |
|---|---|---|---|
| Q1 | 模型只看到前 ~30k 字符的记忆（50 个文件里单个 ≤8k 的那些）。uid 3 的 main 有 43 个文件、约 232KB，模型大约只看见 1/4 | `snapshotMemory` | “已有近似记忆就跳过”这条指令在 3/4 的记忆上失效，只剩下词法强匹配兜底 |
| Q2 | 每个会话摘录取的是最后 16 轮里**末尾** 5000 字符 | `buildExcerpts` | 助手的长回复把用户原话挤掉；而偏好、纠正、身份信息恰恰在用户发言里 |
| Q3 | 提示词没说明哪些值得记、哪些不该记，也没解释四种类型的含义 | `buildPrompt` | 容易写出一次性任务状态、代码里就能查到的事实、相对日期（“昨天”） |
| Q4 | 提示词和 JSON schema 仍允许 `deletes ≤ 8`，但写入时一律拒绝 | schema / `planAddOnlyCreates` | 模型白白输出删除项，浪费输出 token |
| Q5 | 回执固定写“新增 X、更新 0、清理 0”，而 v1 只会新增 | `formatAutoDreamReceipt` | 用户以为它会改、会删 |
| Q6 | 只增不改：没有合并、没有更正、没有修剪，记忆只会越积越多 | 设计（c612644bd，有意的安全契约） | 37/43 条是带日期的 `project` 流水；有一个文件 131KB，超出快照上限，永远看不到 |
| Q7 | 自动写入的记忆 30 天后静默过期，即使一直有用也不会续期 | `memoryTtl.ts` | 有价值的自动记忆会自己消失 |
| Q8 | 去重只有词法匹配（NFKC + 分词覆盖率），没有语义判断 | `memoryLexical.ts` | 换个说法就会写出重复记忆 |

## 5. 与业界的差距

| 维度 | Claude Code auto-memory / dream | ChatGPT memory | Letta / MemGPT | mem0 | V5 个人版 |
|---|---|---|---|---|---|
| 入口 | 设置开关 + `/dream` 手动 + 后台任务面板 | 设置页开关，可查看、可删除 | ADE 可视化 | API | **无开关**（Q0） |
| 写入时机 | 每轮轻量提取 + 24h/5 会话的整理 | 对话中写入 + 后台参考聊天记录 | 热路径工具 + sleep-time agent | 每次 add：提取 → 检索 → 判决 | 主代理在对话中写；dream 24h/5 会话 |
| 整理动作 | 合并、改写、删除矛盾、相对日期转绝对、修剪索引 | 自动合并近似条目，用户可删 | 重写 core block | ADD / UPDATE / DELETE / NOOP | 只能 ADD |
| 去重依据 | 读完整个目录后由模型判断 | 语义 | 语义检索 | 向量 top-k + LLM 判决 | 词法 + 1/4 快照 |
| 容量控制 | 索引 ≤200 行 / 25KB，每条一行 | 满了提示清理 | core 有字符上限，溢出到 archival | 靠 UPDATE/DELETE | 注入索引有上限，文件本身无上限 |
| 写什么 | 明确的四类定义 + 不该存清单 | 偏好、身份、长期目标 | persona / human block | 事实三元组 | 只有一句“稳定、有用的事实” |

## 6. 改进清单（按收益排序）

| 序 | 改进 | 收益 | 风险 | 本轮 |
|---|---|---|---|---|
| 1 | 恢复 v1 记忆整理的开关（管理中心 → 记忆），写明节奏、成本、只新增、30 天到期；仍要求 Max；打开 v1 时后端会自动关掉遗留的 v2 | 功能从 0 次运行变成可用 | 低：可选开启，策略失败即关闭，后端早已在线 | ✅ |
| 2 | 提示词里带上**全部**记忆的紧凑索引（文件名、类型、名称、描述），正文仍按 30k 预算 | 去重覆盖率从约 1/4 提到全部 | 低：只改提示词，约多 7k 字符 | ✅ |
| 3 | 会话摘录优先保留用户发言（逐条保留、单条截断），助手回复只保留头尾 | 偏好和纠正不再被挤掉 | 低 | ✅ |
| 4 | 提示词借鉴 Claude Code：四类定义、不该存清单、绝对日期、每个文件一个主题、描述写成检索钩子、宁缺毋滥；schema 把 `deletes` 收紧为 0 | 写出的记忆更干净，不再浪费输出 | 低：schema 只会更严 | ✅ |
| 5 | 回执和报告卡只报“新增”，并说明自动记忆 30 天到期 | 用户预期正确 | 低 | ✅ |
| 6 | 更新、合并、删除改为“建议 + 用户确认”（类似 mem0 的 UPDATE/DELETE，复用项目记忆候选的模式） | 记忆不再只增不减 | 中：改动 ADD-only 契约的边界，需要单独设计和审批 | 后续 |
| 7 | 自动记忆被再次确认或被使用时续期；到期前提醒 | 有用的记忆不会消失 | 中：会改动已有文件 | 后续 |
| 8 | 语义去重（向量） | 换个说法也能识别重复 | 中：需要嵌入模型，有成本 | 后续 |
| 9 | “立即整理”手动按钮（对应 Claude Code 的 `/dream`），每天限一次 | 可控、可演示 | 低到中：属于用户主动付费 | 后续 |
| 10 | 记录每次运行的 token 用量和耗时，加单次 token 上限 | 成本可观测 | 低 | 后续 |
| 11 | 清理遗留的 `auto_optimizer_enabled=true`（uid 3） | 状态一致 | 需要用户决定 | 交给用户 |

不做的：放宽 v2 的遥测门槛，或绕过 Max 要求。这两项都属于削弱门禁。
