**关键设计修正**(v3 跟 v2 在哲学上的差异):

## 1. 目标(双合同,收敛后)

S12e 不是"一根 trace 走 5 段",而是**两个独立 trace 合同**+**一处 best-effort env 转发**。这跟主计划 §S12e 的"5 段透传"措辞有偏差 — 偏差合理性源于事实底座 §0.1.3:node-agent 字节透传 + CCB env 一次性 spawn,这两个事实让"一根 trace 走 5 段"在物理上做不出来,**强行做出来也是 mock-only,生产假阴/假阳概率高**。

### 合同 A:`connectionTraceId`(连接级)

WS bridge 连接一开始就贯穿到 container WS 连接结束,只随 WS lifecycle 走,不随单条消息变。

**3 段硬门**:
- A.1 master `userChatBridge.startBridge` 创建/复用一个 UUID(就是现 `connId`),所有 bridge 内 log 必带
- A.2 master → node-agent tunnel WS upgrade header `X-Connection-Trace-Id`,node-agent tunnel.go 读取并 bind 到 slog,"tunnel opened" log 必带
- A.3 in-container gateway `handleWsConnection` 读 header,WS 上 stash `_connectionTraceId` 私有字段(沿用 `_userId` 模式),该 WS 连接所有 log 必带(v3 BLOCKER 2 应对)

### 合同 B:`traceId`(单 turn 级)

一次用户消息 inbound→outbound 完整 round-trip 内必带。

**3 段硬门**:
- B.1 master 收 InboundFrame 时**强制生成 canonical** `traceId`(16 bytes hex);若客户端 frame 携带 `clientTraceId` 字段则另存(observation only,不替代 canonical)
- B.2 in-container gateway sessionManager 处理 InboundFrame 时,turn-scoped logger 必带 `traceId`(来自 frame),所有该 turn 内 log 行(含 stream event / completion)必带
- B.3 master outbound forward 给前端时,OutboundFrame 携带 `traceId`,bridge log "turn complete" 必带

### 合同 C:`OPENCLAUDE_TRACE_ID` env(best-effort,不计硬门)

CCB 子进程 spawn 时通过 env 注入**首次** turn 的 `traceId`。受 spawn 模型限制,后续 turn 无法刷新 env;CCB 子进程内部如何用 / 是否记入自己 log 是 CCB 仓事,**S12e 不验证**。

**真要做 CCB per-turn trace**:要走 stdin JSON-RPC 或 runner protocol 扩展,**不在 S12e 范围**(留 S11c / S11a)。

### 合同 D:deploy verify(辅助探针,不计硬门)

smoke-v3.sh 每条 curl 加 `X-Trace-Id: smoke-<safeTag>-<hex>` header,部署后 ssh master journalctl 抓 ≥3 条命中 → warn-mode 报告。**只证 master HTTP 段透传**,不证 WS / node-agent / container 段(smoke 不开 WS)。S12e 第一版接受这个限制,完整 deploy 链路 trace 验证后置 S11a `v3 trace` 命令。

### 完成定义(取代 v1)

- protocol 包 `InboundMessage` / `OutboundMessage` 新增 `traceId?: string` + `clientTraceId?: string` 字段(camelCase,Optional)
- 新增 `packages/protocol/src/traceId.ts`:`newTraceId()` + `parseTraceIdCandidate(raw)` 双 primitive runtime helper(v3 MAJOR 1 应对,拆分 v2 的 `normalizeTraceId`)
- 合同 A 3 段、合同 B 3 段全部硬门(单元测试 + mock e2e 集成测试断言每段 log 必带对应字段)
- 合同 C env 注入到位即可,无 e2e 断言
- 合同 D smoke 加 header + warn-mode 校验
- 标准字段在每段 log 的字段矩阵(§3.5)单测/集测断言
- 不引入 principal 三字段
- Go node-agent tunnel + 主 routes slog 加 camelCase `connectionTraceId` 字段
- 文档 §3 即 contract,无须独立文件(规模够小)

## 3. 设计要点

### 3.0 trace helper(v1 BLOCKER 2 + v3 MAJOR 1 应对,实施前置硬要求)

事实底座 §0.1 + Codex 一审 BLOCKER 2 揭示:gateway / userChatBridge 现状是 `JSON.parse(...) as InboundFrame`,**TypeBox schema 不参与运行时校验**。若不补 runtime helper,plan §3.7 的 D2/D3(信任客户端 traceId)前提全空。

Codex 二审 MAJOR 1 进一步指出 v2 的 `normalizeTraceId` 返回 `{traceId, source, valid}` 签名语义错位 — valid=false 时返回的 traceId 是新生成的(跟 raw 无关),让调用方理解困难。v3 拆成两个清晰 primitive,调用方自己组合 fallback。

新增文件:`packages/protocol/src/traceId.ts`,导出:

```ts
export const TRACE_ID_REGEX = /^[A-Za-z0-9_-]{16,64}$/

/** 16 bytes hex, 32 chars. 跟 ensureRequestId 完全一致(randomBytes(16).toString('hex'))。 */
export function newTraceId(): string

/** parseTraceIdCandidate 的 issue 枚举(给 logger 用,**不带 raw 值**,防 log injection)。 */
export type TraceIdIssue =
  | 'missing'        // undefined / null
  | 'wrong-type'     // 非 string
  | 'empty'          // 空字符串
  | 'too-short'      // < 16
  | 'too-long'       // > 64
  | 'bad-charset'    // 不符 regex 字符集

/**
 * 校验 raw 是否符合 trace id 字符集 + 长度。
 * - 合法:返回 { ok: true, traceId: raw }
 * - 非法:返回 { ok: false, issue }  — 调用方决定 fallback / log / drop
 *
 * 不在 helper 内 fallback,因为不同调用点 fallback 策略不同:
 * - master inbound canonical 生成 → 直接 newTraceId(),不看 client 值
 * - gateway WS upgrade connection trace → ok 用 raw,issue 用 newTraceId() + warn
 * - master observation clientTraceId → ok 存 logger,issue 只记 issue 名不存 raw
 */
export function parseTraceIdCandidate(
  raw: unknown,
): { ok: true; traceId: string } | { ok: false; issue: TraceIdIssue }
```

**强制调用点**(实施时由测试断言覆盖):
- master `userChatBridge.ts` 收 InboundFrame:`turnTraceId = newTraceId()` + `parseTraceIdCandidate(frame.clientTraceId)` 处理客户端可选值
- master 控制面 / 数据面发起前:无需 parse(用上面已生成的 canonical 直接传 header)
- gateway `server.ts` `handleWsConnection` 内读 `X-Connection-Trace-Id`:`parseTraceIdCandidate(req.headers['x-connection-trace-id'])`,ok 用 raw,issue 用 `newTraceId()` + warn
- Go node-agent 同样语义(`internal/trace/parse.go` 实现 Go 版 `ParseTraceIDCandidate`)

**安全合同**:
- master **永远** 自己生成 canonical `traceId`(不信任客户端 turn-level)
- 若客户端 InboundFrame 携带 `clientTraceId` 字段且 `parseTraceIdCandidate` ok,**只作为 observation** 存进 logger context(允许前端 join 自己日志),**不替代 canonical**
- master canonical `traceId` 是日志查询/diagnostics 的唯一权威字段
- **非法 clientTraceId** 不进 logger raw 值字段,只记 `clientTraceIdIssue: <enum>`(防 log injection / 防超大字符串膨胀)

### 3.1 双合同结构(camelCase 全文统一)

| 合同 | 字段名 | 生命周期 | 生成点 | 用途 |
|------|--------|---------|--------|------|
| A | `connectionTraceId` | 一个 user↔container bridge WS 寿命 | `userChatBridge.startBridge`(复用已有 `connId = randomUUID()`) | 关联整个 bridge 内所有日志(open/close/重连/心跳) + node-agent tunnel + container WS conn |
| B | `traceId` | 一次用户消息 inbound→outbound round-trip | master 收 InboundFrame 时 `newTraceId()` **永远** 重新生成 | 关联单次 turn 全链路日志 |
| B' observation | `clientTraceId` | 同 B | 客户端 InboundFrame.clientTraceId 字段(若有且合法) | 仅 observation,允许前端 join,不替代 canonical |

格式:`^[A-Za-z0-9_-]{16,64}$`。canonical 默认 32-hex(跟 `ensureRequestId` 完全一致,`randomBytes(16).toString("hex")`)。connId 是 36-char UUID 含 hyphen,正则兼容。

HTTP/WS header:
- `X-Trace-Id` — turn-level(用于 deploy smoke / HTTP route 控制面)
- `X-Connection-Trace-Id` — connection-level(用于 WS tunnel upgrade)

(NIT 4:两个 header 名分开,避免误读 — turn 级和 connection 级语义不一样,header 同名会让 node-agent 中间日志写错字段。)

### 3.7 决策点(v3)

| # | 问题 | v3 决策 | 理由 |
|---|------|--------|------|
| D1 | 连接级 trace 复用 connId 还是新生成? | **复用 `connId`** | connId 已是 randomUUID,复用减状态。字段名叫 `connectionTraceId`(MAJOR 2 应对,不混 turn trace 命名) |
| D2 | 客户端传 traceId 时如何处理? | **master 永远生成 canonical `traceId`,客户端值另存 `clientTraceId`(observation only)** | v1 写 TOFU(信任客户端值)— 缺少 runtime 校验;Codex 二审 MAJOR 8 指出 v2 "billing 借壳" 论据夸张(billing 用独立 `requestId` 字段),v3 移除该论据。**保留两条真实理由**:(a) audit 需要唯一权威源,服务端生成保证 traceId 不可伪造;(b) 客户端可塞超长/特殊字符串作 log injection,master canonical 隔离后 raw 值由 `parseTraceIdCandidate` issue 枚举吸收,不入 logger raw 字段 |
| D3 | 非法 trace id(`parseTraceIdCandidate ok=false`)? | **fallback 生成新 canonical + warn log,log 只带 issue 不带 raw 值** | 观察字段不应阻业务;但要保留 warn 行(高频会暴露客户端 bug 或攻击);**MAJOR 2**:不带 raw 值防止超长字符串膨胀 + log injection |
| D4 | CCB 子进程 env `OPENCLAUDE_TRACE_ID`? | **首 turn 注入,best-effort,不计硬门**(合同 C) | v1 写"首 turn 注入"但仍列入 5 段贯通;v3 改成"best-effort,不算贯通硬门",真要 per-turn CCB trace 后置 S11c stdin JSON-RPC 扩展 |
| D5 | turn-level vs connection-level 字段命名? | **双字段独立命名:`traceId` + `connectionTraceId`** | 不同生命周期、不同合同(A vs B)、不同 header(`X-Trace-Id` vs `X-Connection-Trace-Id`) |
| D6 | smoke trace 探针失败是 abort 还是 warn? | **warn-mode**;文档明确"只证 master HTTP 段日志透传" | smoke 不开 WS,本来就证不了 WS / node-agent / container 段;abort 风险大,warn 给 deploy 操作员可见信号即可;完整链路 verify 等 S11a `v3 trace` 命令 |
| D7 | turn outbound trace 来源(v4 BLOCKER 1) | **server.ts `dispatchInbound` 是唯一 wire stamp 点**:为每个 turn 创建 `outEnvelope = { traceId: frame.traceId, ... }`,4 类 outbound 出口(message / error / codex_billing / permission_request)都从 outEnvelope 复制 traceId 到 public `traceId` 字段;sessionManager 完全不碰 wire frame trace 字段;master 只校验 mismatch,不回填 | v2 "master 从 active turn context 补"在并发多 turn 下会错归属;v3 把 ownership 放在 sessionManager closure 上又留了"private→public"转换缺口;**v4/v5** 把 stamp 点收敛到 dispatchInbound 单一函数 — 5 个出口(实际 4 类 + 1 类显式排除)在同一函数 scope 内一目了然,认知负担最低 + 没有 private 字段链。`permission_settled` 因 lifecycle 跨 turn 显式排除(v5 BLOCKER 2,见 §3.2 B.2) |
| D8 | gateway WS 连接上下文(BLOCKER 2) | **在 WS 和 frame 上 stash `_connectionTraceId` 私有字段**(沿用 `_userId` 模式);不引入 WebSocketContext 类型 | v2 用了不存在的"WebSocketContext"抽象;现代码 gateway 是 `handleWsConnection(ws, req)` + 全局 stash 私有字段,扩展同模式认知负担最低 + 跟 deliver 路径既有 `_userId` strip 逻辑天然对齐 |

### 8.2 W3C `traceparent` 兼容预留(NICE)— 信任边界(MAJOR 7 应对)

未来若要对接 OpenTelemetry 生态(Grafana Tempo / Datadog APM 等),关键是**区分入站源是否可信**:

**永远不信任的入站源 → 永远 master canonical**:
- 公网浏览器 WS bridge(`/ws/user-chat-bridge`)— 客户端可伪造 traceparent
- 公网浏览器 HTTP API(`/api/*` 现有路由)
- 任何 unauthenticated 入站
- 客户端 `traceparent` header 处理(v4 MAJOR 6 应对,**收紧**):
  - **不**把完整 `traceparent` 字符串(`00-{32-hex traceid}-{16-hex parentid}-{2-hex flags}`)塞 `clientTraceId`(格式不同 — clientTraceId 是平字符串,traceparent 是 4 段 `-` 分隔)
  - 未来若引入,加专用函数 `parseTraceparentHeader(raw): { ok, traceId, parentId } | { ok: false, issue }`,**只取中间 32-hex `trace-id` 段** + 再走 `parseTraceIdCandidate` 校验,通过后塞 `clientTraceId`
  - 完整 `traceparent` 字符串 raw 不入 logger(否则字段值含 `-` 触发格式不一致)

**可信入站源 → 未来可派生 canonical**(S11c 范围,**S12e 不实现**):
- internal service-to-service HTTP(若加,需 mTLS 鉴权)
- node-agent → master 反向调用(已 mTLS,逻辑上可信)
- internal cron / scheduled tasks 内部触发(无远端)
- 这些场景下,**若入站带 W3C `traceparent`**,可由 trusted-ingress 中间件解析 `trace-id`(32 hex)作为 canonical `traceId`,跟 master 自己 newTraceId() 等价

**S12e 最小迁移代价的设计选择**:
- canonical 格式 `^[A-Za-z0-9_-]{16,64}$` 兼容 W3C 32-hex traceparent trace-id 段
- `parseTraceIdCandidate` 可在未来加一个 `parseTraceparentHeader(raw): { ok, traceId, parentId } | { ok: false, issue }` 兄弟函数
- 应用 frame 内仍传 `traceId` 平字段(避免每段都解析 traceparent,降本)
- OTel 桥接候选路径:加 `internal/trace/exporter.ts`(TS)/ `internal/trace/exporter.go`(Go)把 logger 已有 `traceId` 输出为 OTel SpanContext

S12e 只用 §3.0 helper 设计 + 字段格式让上述迁移代价低,**不**在 S12e 实现任何 traceparent 解析路径。

- master HTTP routes(router.ts)未深度接入 trace contract(只补一处 `X-Trace-Id` header → child),非 5 段链路硬门
