# v3 商业版团队模式易用性计划表（2026-06-12）

目标：团队模式默认行为必须更符合用户直觉，所有修复不得降低现有易用性。

| 优先级 | 问题/优化点 | 用户影响 | 处理方案 | 验收方式 | 状态 |
|---|---|---|---|---|---|
| P0 | 团队运行中点“停止”可能发给会话默认 Agent，而不是团队队长 | 用户以为已停止团队任务，实际队长进程可能继续跑，造成困惑和额外成本 | 停止按钮、`/stop`、思考超时兜底、重新生成前的 stop 都读取当前 turn 的团队队长 | 静态测试覆盖 stop 路由；Web 测试通过 | 已实施 |
| P0 | 团队回答点“重新生成”会退回单 Agent/default model | 用户选择了团队，但 regen 结果不像团队协作 | 用户消息持久化 `_teamRun` 元数据；regen 复用原团队队长、原团队 prompt、原团队模型覆盖 | Web 测试覆盖 `_teamRun` 持久化与 regen 路由 | 已实施 |
| P1 | 团队选择使用全局 localStorage key，切账号/切会话容易串状态 | 共享浏览器或多账号场景下，错误继承上一个用户的团队选择 | 改为 user-scoped 存储；当前会话记录 `_selectedTeamId`；切会话同步选择；登出清理 | Web 测试覆盖 user-scoped key、logout 清理和 session sync | 已实施 |
| P1 | 团队 prompt 中“不要假设浏览器工具可用”等说明会误触发 browser toolset | 普通团队任务被挂载额外浏览器工具，降低稳定性/启动速度 | gateway toolset intent 对 `# Agent Team Run` 只分析 `## 用户目标` 原文 | Gateway 单测覆盖团队 prompt 不误触发 browser | 已实施 |
| P2 | 团队模式的失败恢复/离线排队缺少清晰边界 | 队长路由与 active team 状态可能被残留状态影响 | 队列满/turn 结束/stop 统一清理 turn-scoped `_activeTeamRun` | 现有 stop/regen/web 测试覆盖 | 已实施 |
| P2 | 团队模式说明与后续优化缺少集中追踪 | 后续改动容易只修局部，体验不一致 | 本文件作为后续团队模式 UX backlog，新增项继续追加 | 文档落盘且随代码一起评审 | 已完成 |

后续可选优化（本轮不改动产品交互大结构，避免降低易用性）：

- 团队运行过程可视化：把“队长/成员/复核/缺口”显示成可折叠时间线。
- 团队配置向导：从“任务类型 → 推荐团队 → 角色确认”三步创建，减少表单感。
- 团队运行预检：发送前提示缺失 agent、未配置复核、并发数过高等风险。
- 团队结果质量模板：按团队类型预设最终输出格式，减少用户改 prompt 的成本。
