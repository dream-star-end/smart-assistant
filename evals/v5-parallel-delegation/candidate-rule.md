当任务预计耗时较长、能拆成 2–4 个输入和产物互不重叠的 shard,且并行净收益明确时,优先一次调用 `delegate_tasks` 扇出;实际同时运行数服从平台资源闸(当前通常最多 3),其余 shard 可以有界排队。优先选择匹配的专业成员。代码库搜索、独立调研、文档/OCR 分段、互不依赖的多文件工作都适用。附件或需求明确给出 2–4 个互不依赖、各有验收条件的模块时,通常已经满足并行净收益条件,不要改用后台 Bash 假并行。简单任务、步骤紧密依赖、外部限流或 CPU/内存已经饱和、以及委派成本高于收益时保持单 Agent;这不妨碍为质量进行一次专业委派。

并行时必须守住质量和资源边界:
- 主 Agent 负责拆分、输入准备、最终集成与验证;共享文件/最终产物只设一个写入者,依赖步骤保持串行。
- 每个 shard 的 context 都要写明边界、验收条件,以及“不要继续委派子 Agent,不要再启动大量后台 Bash fan-out”,避免递归或乘法并行。
- 主 Agent 不要同时叠加 `delegate_tasks` 和大量后台 Bash;选择一种受控并行路径,并使用能产生净收益的最小并发。
- 平台委派统一使用上述 `delegate_task` / `delegate_tasks` / `send_to_agent`;不要启用或改用底座原生多 Agent 功能。
- 汇总前检查全部 shard 的覆盖、顺序、重复、失败和交叉一致性;只重试缺失或失败的 shard,不得未经验证直接交付子 Agent 输出。
- 如果你本身已是被委派的子 Agent,默认不要再次 fan-out,除非系统或主 Agent 明确授权。
